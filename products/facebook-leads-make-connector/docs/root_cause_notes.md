# Where this came from

Surfaced by the Opportunity Engine's `discourse_forums` connector
(`community.make.com`), ingested 2026-08-07. Two real, current, unresolved
threads — read in full via Discourse's public `.json` API, not paraphrased
from the engine's one-line opportunity summary:

## Thread 1 — retrieval fails even with every permission granted

**"Facebook Lead Ads – GraphMethodException 100 when retrieving test lead"**
(community.make.com topic 113073, posted 2026-08-07, author Monica Cacciani)

- Scenario: single Facebook Lead Ads module, webhook trigger, connected to a
  real Page (AreaLifting).
- Webhook fires correctly on a test lead.
- The `GET /{leadgen_id}` call that should retrieve the lead's field data
  fails: `[400] ... Object with ID '1930628924301148' does not exist ...`
  — `GraphMethodException`, code 100.
- Everything Meta's UI exposes was already checked and correct: webhook
  active, Make registered as a Business Integration, "Access leads for your
  Pages" permission granted, Lead Access settings checked.
- No fix offered in the thread. Author asks whether it's a known Make/Meta
  bug needing a backend fix.
- **Our diagnosis** (`docs/SETUP.md` walks through checking this): Meta's own
  docs list four scopes required specifically for lead retrieval
  (`ads_management`, `leads_retrieval`, `pages_show_list`,
  `pages_read_engagement`). "Access leads for your Pages" in the UI does not
  obviously map to `leads_retrieval` being granted on the actual token in use
  — and even with every scope granted, a Page token generated by a user who
  isn't an advertiser on the ad account the lead's form belongs to fails the
  same way. Neither of these is stated anywhere in the error message.

## Thread 2 — multi-form Pages break Make's static field mapping

**"Facebook instant form integration to Outlook"**
(community.make.com topic 113090, posted 2026-08-07, author Lee Wilson)

- Goal: one Make scenario — `Facebook Lead Ads (New Lead) → Get Lead Details →
  Microsoft 365 – Send an Email` — capturing every lead from **several**
  Instant Forms on one Page, without duplicating the scenario per form.
- Symptom: works when tested with hand-entered data; fails end-to-end because
  the Outlook module isn't receiving field data from the forms.
- Root technical question asked outright: "should be using New Lead, New Lead
  Multiple, Get Lead Details, or another approach for multiple forms on the
  same Page?" — nobody in the thread had a real answer.
- **Community's own workaround** (from a "Community Champion," not Make
  staff): give up on Make's native module entirely, have every form dump into
  one shared Google Sheet, and have Make watch the sheet instead. This routes
  around the problem; it doesn't solve it, and it adds Google Sheets as a
  fragile middle layer with its own failure modes.

## Why these two threads together are a real, buildable opportunity

Facebook's own Graph API is consistent underneath both problems: standard
fields (`full_name`, `email`, ...) always use the same internal `name`
regardless of the form; custom questions get a slugified version of the
on-form question text, which is different on every form. Make's native
module maps fields statically per scenario — so it was never going to handle
multiple differently-shaped forms cleanly, and its UI gives no diagnostic
path when the *retrieval* call itself fails for permission reasons that
aren't visible from Make's side at all.

`src/leadbridge/` fixes both by moving the variable part (talking to Facebook)
out of Make entirely: one normalization layer that always emits the same
flat JSON shape to Make, with the retrieval failure mode diagnosed instead of
opaque. See `tests/test_normalizer.py` and `tests/test_graph_client.py` for
the concrete fixture-based proof both problems are actually fixed, not just
described.
